# Issue中心の共通運用

GitHub Issuesを受入条件・状態・依存関係・検証証拠・次の作業の正本とする。
[実装戦略](../implementation-strategy.md)の優先順と範囲、
[計画の安全原則](../implementation-plan.md#permanent-safety-invariants)、
承認済みADR、[脅威モデル](../security/threat-model.md)を守る。

1. 初回にgit状態、対象Issue、PR head、既存変更を確認する。元のユーザー変更は保持する。
   毎回読むのは本書、対象Issue、関連差分、検証結果を基本とし、設計文書は関係箇所だけ読む。
2. 受入条件を「実証済み／不足／外部環境待ち」に分け、対象commitと証拠リンクをIssue本文に残す。
   元の受入条件を削除・緩和しない。過去の報告・古いCI成功を現在の完了証拠にしない。
3. 依存関係に沿って不足分を一つの実装単位にまとめる。採用済みIssueの企画審査は繰り返さない。
   優先順は #4・#5・#14 → #6・#7・#8 → #9 → #11。#10・#12・#13は主要機能の依存部分を先行する。
4. 原則1人が実装し、別担当が独立レビューする。子エージェントには対象・受入条件・ファイル・制約だけ渡す。
   長い会話履歴は渡さない。同じファイルを同時編集しない。レビューはcommitまたは差分を明示する。
5. ローカルは変更に関連するテスト、失敗経路、必要なrace・静的検査に絞る。
   まとまった変更をpushしてCIを実行し、短間隔で確認しない。最新headと全必須結果を照合する。
   未実施・skip・外部環境不足は成功でない。メモリ、実DB、模擬Provider、実AWSを区別する。
6. Issue本文の状態・証拠・残課題を更新する。CI開始だけで完了にしない。
   引き継ぎは「Issue、commit/PR、完了条件、検証証拠、残課題、次の一手」のみ、原則20行以内。

安全原則: 認可・Journal予約・Auditの失敗はfail-closed。UNKNOWNを再Writeの許可にせず、
read-only Reconcileを使う。MISSING/INCONCLUSIVEをPASSにしない。秘密情報を証拠へ載せない。
主要機能を優先し、自動運転機構の追加開発を進めない。

利用上限・期限・解消できない障害ではIssueとcommit/PRに状態を保存して停止する。
自動reset、credits購入、再試行ループは行わない。今回の範囲は実装・レビュー・テスト・CIまで。
merge、本番deploy、実AWSの有料操作は含まない。

既存の[補助ツール用packet形式](packet-format.md)は補助ツールを明示的に使う場合だけ参照する。
古い五役運用・日付付き作業記録は必須手順ではなく、本書が日常運用に優先する。
