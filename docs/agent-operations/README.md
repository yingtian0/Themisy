# 自律開発の運用契約

Themisyの固定されたECS MVPを、企画、審査、実装、独立レビュー、CI・テストの順に改善するための運用規約です。これは運用手順であり、スケジューラの稼働や無人再開を保証するものではありません。実際の起動・状態保存・停止は実行管理側が担当します。

判断基準は [implementation plan](../implementation-plan.md)、READMEのECS MVP範囲、承認済みADR、[脅威モデル](../security/threat-model.md)です。Issueがタスク受入条件の正本です。引き継ぎは過去の観測記録なので、着手前に現行コードとCIを再確認します。SQL状態更新の旧不具合や、recovery/manifestの基盤を未実装と決めつけて再実装しません。

## 5つの役割

| 役割 | 入力と責任 | 出力 |
|---|---|---|
| 企画・アイデア担当 | 固定ゴール、顧客課題、未達のrelease gateから候補を作る | 課題、代替案、期待効果、検証方法 |
| 企画レビュワー | 既存CI/CD＋IAMを含む代替構成と比較する | 採用・修正・保留・却下、根拠と未確認事項 |
| マネージャー | 採用案を一つの変更範囲に分解し、予算・依存・所有権を管理する | 受入条件付きpacket、割当、checkpoint、終了報告 |
| 実装者 | 指定worktreeと範囲で実装・失敗経路試験を行う | 差分、対象commit、実行した検証、制約 |
| 実装レビュワー | 仕様・差分・テストを独立に確認する | 対象commitに結び付いた合否、再現手順、残存リスク |

提案者は企画承認を、実装者は実装承認を兼任しません。マネージャーは不合格を独断で合格にしません。採用済みの不具合修正は企画審査を繰り返さず、その採用根拠を参照できます。

## 一巡の手順

1. 最新Issue、git status、基準commit、既存変更、前回checkpointを読む。
2. 受入条件・対象外・期限・検証コマンドをpacketに固定し、単独所有権を取得する。
3. 実装者が変更し、必要な境界の失敗経路を検証する。
4. 別担当が対象commitをレビューする。指摘にはファイル・再現条件・影響を付ける。
5. 要修正なら最大3回の修正サイクルを行う。初回レビューは修正回数に含めない。3回後も不合格ならblockedとし、設計判断を記録する。
6. 合格した同一commitで所定のCI・テストを確認して完了する。統合によりcommitや内容が変わった場合は、統合後の検証とレビューの適用範囲を再確認する。
7. 依存しない次の採用済みpacketへ進む。候補が尽きたら、変更を作り出さずcheckpointを残す。

標準確認は `make fmt-check`、`make test`、`make test-race`、`make lint`。DB/Temporal/AWS試験は別々に成否を記録します。未実施・skip・環境不足は成功ではありません。CI開始とCI成功は別の状態です。

## 状態・所有権・再開

packetの論理状態は `proposed → approved → claimed → implementing → reviewing → verifying → done`。修正は `reviewing → implementing`、待機は `blocked`、期限・予算での終了は `stopped` とします。これは [packet例](task-packet.example.json)の概念上の契約であり、実行ツールのCLIや内部形式とは別です。

- 保存は原子的に行い、更新にはversionの比較を用いる。変更履歴には時刻、旧状態、新状態、担当、理由を追記する。
- 所有権はtask ID、owner ID、lease期限、世代番号で識別する。同時に一人だけが変更できる。更新には現在の世代を必要とする。
- lease切れは担当の停止確認を始める条件であり、旧担当の書込み継続を許したまま再割当してはいけない。旧担当を停止・隔離してから世代を進める。
- checkpointには対象commit、worktree、未コミット差分の保存先、変更ファイル、テスト結果、未終了プロセス/CI run、次の一手を残す。秘密情報は保存しない。
- 再開時は所有権、時刻・予算、作業ツリー、commit、CI状態を再照合する。実行済み操作をcheckpointだけで推定して再実行しない。
- 外部pushやCI起動などの操作は識別子を記録し、不明な結果を確認してから続ける。

本資料自体はロックやleaseを実装しません。実行管理がこれらを未実装なら、単一マネージャーが逐次割当し、終了確認後だけ引き継ぐ運用に限定します。

## 時間・使用量による停止

期限はタイムゾーン付き絶対時刻で保存し、比較にはUTCを使います。期限と利用上限のうち先に来たものを優先します。5時間を目標にしても、上限を超えて継続しません。

各タスク開始前、レビュー引継ぎ時、長い処理の前後に残時間と取得可能な使用量を確認します。期限15分前を新規実装の開始停止目安とし、残時間は検証・保存・報告に充てます。期限到達時は新規操作を開始せず、子エージェントと処理を安全に停止します。停止できないCI等はrun IDと状態を記録します。

使用量が取得不能なら推定値を残量として扱いません。サービスが制限を返したら停止し、自動再試行ループや自動credits購入・reset消費は行いません。回復後の再開には新しい実行時間枠と所有権確認が必要です。完了未達のpacketをdoneにしてはいけません。

今回の時間枠の記録例は [tonight example](tonight-2026-10-11.md)です。毎日の定期実行設定ではありません。

## 製品と開発作業の境界

- 本番資格情報、本番write APIには接続しない。AWS stagingは専用環境と明示された権限・費用範囲でだけ実施する。
- Agent/CIに任意AWS操作、ARN、role、shell、URLを選ばせる経路を追加しない。
- 自律企画やエージェントの判断をProduction Writeの承認源にしない。
- audit失敗、認可不明、証拠不足はfail closed。MISSING/INCONCLUSIVEをPASSに変えない。
- at-most-once、独立context照合、署名結果、実runtime health、IAM迂回拒否の未達を隠さない。
- ユーザー所有変更を保護する。merge、公開、production操作、対外メッセージはそれぞれの権限範囲を確認する。本手順だけではそれらを許可しない。

競合評価の根拠と仮説は [product assessment](product-assessment.md)に分けて記録します。

## 単一マネージャーの実行補助

`python3 scripts/agent_cycle.py --worktree /absolute/dedicated-worktree --state-dir /absolute/local-state --until 2026-10-12T03:00:00+09:00` で、Codex CLIによる上限30分の管理セッションを逐次起動できます。期限は毎回指定します。`progress`のときだけ次へ進み、`idle`、`blocked`、非ゼロ終了（利用制限を含む）、不正な結果、タイムアウトで停止します。タイムアウト後は自動で同じ変更を再試行しません。

Git共通ディレクトリのOSロックで同じリポジトリへの補助プログラムの二重起動を防ぎ、ローカル状態と各セッションのJSONLを保存します。CLIは`--approve-for-me`でworkspace-write sandboxと自動承認レビューを使います。許可されない操作や環境不足はblockedにし、制限を迂回しません。ログにはソースやツール出力が含まれるため、state-dirはローカルに保管してGitへ追加しないでください。

この補助は[packetの形式](packet-format.md)に従い、対象commit・独立レビュー・必須チェックの記録の整合性を検証します。証拠の真正性や製品の正しさは独立レビューとCIで確認します。リモートCI未実施は`local_only`として保存し、リリース完了とは扱いません。packet例のlease/CAS機構は未実装で、単一マネージャーの逐次割当運用です。手動起動した別エージェントをOSロックで止めることはできないため、同じworktreeで併走させません。今回の対話内マネージャーが稼働中は、この補助を重ねて起動しません。

`--task-file /absolute/task.txt`で今回許可した作業範囲を絞り、`--max-cycles 1`で一巡だけ検証できます。Python 3.11以上とCodex CLIが必要です。中断後は作業と旧プロセスの停止を確認してから`--resume-interrupted`を指定します。期限15分前から新規サイクルを開始しません。プロセス停止は最大2秒の終了猶予を含み、意図的に別sessionへ切り離されたプロセスまで隔離するものではありません。ホストが起動・接続していることが前提です。

既存の同一リポジトリPRへ検証済みcommitを送ってGitHub Actionsの必須5ジョブを待つ場合だけ、運用者が `--ci-pr <番号>` を明示します。このオプションは既存PRの同一ブランチへ候補SHAをpushするだけで、PR作成・force push・mergeは行いません。PRがfork、base branch、別リポジトリ、別SHAへ変化した場合や、期限内に全ジョブが同じSHAで成功しない場合は失敗として停止します。デフォルトはpushしない `local_only` です。
